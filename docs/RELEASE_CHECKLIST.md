| Step | Command | Pass condition |
| --- | --- | --- |
| Types | `npm run typecheck` | 0 errors |

from a working tree with uncommitted changes.

## 2. Reproducible production build

- **Toolchain:** Node 24.22.1 (`.nvmrc`), npm 11.19.1, Windows 10 x64 was used for the
  verified build. `package.json` requires Node `>=20.19.0`.
- **Dependency source:** `package-lock.json` is committed. Always install with `npm ci`
  (never `npm install`) so the lockfile is authoritative.
- **No environment variables or secrets** are required for the build. Vite reads no `.env`
  file for this project.
- **No network assets at runtime.** Fonts are OS system fonts; art, audio, and UI are
  generated by code. The build output is fully static.
- **Deterministic inputs:** source + lockfile + Node/npm versions determine the output.
  Content hashes are stable when those inputs are stable. The build does **not** inject a
  timestamp, so a rebuild of the same commit produces the same functional artifact.
- **Archive the artifact:** `dist/` as `knowledge-realms-<version>-<git-sha>.zip` plus a
  SHA-256 checksum. Keep at least the last three release archives.
- **Recorded build facts (0.1.0):** 21 precache entries (~1,963 KiB), Phaser isolated in its
  own long-lived chunk, service worker generated by `vite-plugin-pwa` (Workbox
  `generateSW`, prompt mode).

Verification commands:

```bash
node -e "const p=require('./package.json'); console.log(p.version, p.engines.node)"
sha256sum dist/index.html dist/sw.js
```

## 3. Version number strategy

- **Format:** semantic versioning `MAJOR.MINOR.PATCH`, starting at `0.1.0`.
- **0.x policy:** minor bumps for new phases/feature sets, patch bumps for fixes and
  release-only changes. `1.0.0` is reserved for the first public graduation release.
- **Single release version, three places:** `package.json` `version`, `src/constants.ts`
  `GAME_VERSION`, and the start-menu footer (`v{GAME_VERSION}`). The first two are kept in
  sync by `tests/release/phase29_5_release.test.ts`; a mismatch fails the suite.
- **Never reuse a version.** If a deployed artifact must be rebuilt, bump at least the patch
  version first.
- **Independent version namespaces** — do not conflate:
  - App version: `package.json` / `GAME_VERSION`.
  - Save data schema: `SAVE_DATA_SCHEMA_VERSION` (currently **6**); bump only when the stored
    payload format changes, together with a migration in `src/storage/SaveMigrations.ts`.
  - Save export envelope: `SAVE_EXPORT_FORMAT_VERSION` (currently **1**).
  - Question content/bank versions: Phase 28.5 formats.
- **No build metadata in the UI.** The version identifies the source commit; the archive
  checksum identifies the artifact.
- **Bump procedure:**
  1. Update `package.json` and `src/constants.ts`.
  2. Run `npm run verify`.
  3. Add a release-notes entry (Section 4).
  4. Commit, tag `v<version>`, archive `dist/`.

## 5. Deployment instructions

The game is a **static site** and can be hosted on any static host that meets the
requirements below. **No host is selected and no deployment has been performed.**

### 5.1 Host requirements

1. **HTTPS** — required for service workers (except `http://localhost`).
2. **Root-path hosting** — the build uses absolute `/assets/...`, `/pwa-icon.svg`,
   manifest `start_url: "/"`, `scope: "/"`, and navigation fallback `/index.html`.
   Hosting under a sub-path is **not supported** without changing `vite.config.ts`,
   `src/pwa/pwaConfig.ts`, and re-testing the PWA flow.
3. **Unknown paths fall back to `/index.html`.** The service worker also provides this
   fallback once installed, but the host must serve the app entry point on a first visit.
4. **Correct MIME types** — `.webmanifest` as `application/manifest+json`, `.js` as
   `text/javascript`, `.css` as `text/css`, `.svg` as `image/svg+xml`.
5. **Cache headers** — `index.html`, `sw.js`, and `manifest.webmanifest` must not be cached
   long-term (`Cache-Control: no-cache`). Hashed files under `/assets/` should be immutable
   (`Cache-Control: public, max-age=31536000, immutable`).
6. **Compression/Brotli** recommended; the Phaser chunk is the dominant payload.
7. **No server-side logic, database, or environment variables** are required.

### 5.2 Deploy steps (host-agnostic)

```bash
# 1. Build the approved commit
git checkout <release-commit>
npm ci
npm run verify

# 2. Archive and checksum
tar -czf knowledge-realms-<version>-<sha>.tar.gz -C dist .
sha256sum knowledge-realms-<version>-<sha>.tar.gz

# 3. Upload the *contents* of dist/ to the web root (not the dist folder itself)
#    Example for an SSH/static host:
scp -r dist/* <user>@<host>:/var/www/knowledge-realms/current/

# 4. Purge the CDN cache for / and /sw.js, then verify:
curl -I https://<domain>/                 # 200, HTML
curl -I https://<domain>/sw.js            # 200, text/javascript, no-cache
curl -I https://<domain>/manifest.webmanifest  # 200, application/manifest+json

# 5. Run the smoke-test checklist (Section 9) against production.
```

### 5.3 Example nginx server block (reference only)

```nginx
server {
  listen 443 ssl;
  server_name game.example.com;
  root /var/www/knowledge-realms/current;
  index index.html;

  location = /sw.js {
    default_type text/javascript;
    add_header Cache-Control "no-cache";
    try_files $uri =404;
  }
  location = /index.html {
    add_header Cache-Control "no-cache";
  }
  location = /manifest.webmanifest {
    default_type application/manifest+json;
    add_header Cache-Control "no-cache";
  }
  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
    try_files $uri =404;
  }
  location / {
    try_files $uri /index.html;
  }
}
```

Do **not** add `Service-Worker-Allowed` rules wider than the site root; the app expects
scope `/`.

## 6. Rollback procedure

Rollback means redeploying the previously archived `dist/` artifact. It is not automatic.

1. **Stop the rollout** (do not upload another build).
2. **Diagnose first** — capture console errors and the failing version; keep the faulty
   artifact until the cause is understood.
3. **Check save compatibility before rolling back.** Save schema is currently **6**.
   - If the faulty release did **not** bump `SAVE_DATA_SCHEMA_VERSION`, redeploying the
     previous artifact is safe.
   - If it did, a rollback to a build that only understands schema ≤ 5 may reject or repair
     newer saves. Prefer a forward-fix. If rollback is unavoidable, first preserve the
     player's browser profile/site data (Section 10) and accept that saves written by the
     newer build may not load.
4. **Redeploy** the previous archive contents to the web root and purge CDN caches for `/`,
   `/sw.js`, and `/manifest.webmanifest`.
5. **Service worker behavior:** already-open clients keep the newer precached build until
   they accept the update prompt. Rolling back changes `sw.js`, so players see
   “Update available — Save & Reload” and activate the older build only on confirmation.
   Players who never open the app again are unaffected.
6. **Verify** the rollback with the Section 9 smoke tests and confirm the start-menu version
   shows the rolled-back number.
7. **Record** the rollback (time, version, reason, data impact) in the incident log.

The in-game service worker never activates a waiting update without the player’s action, so
a rollback cannot yank a session out from under an active player.

## 8. Known limitations

Carry these into release notes; they are current as of Phase 29.5.

**Platform and input**
- Supported target is desktop Chromium (Chrome/Edge) with a keyboard. Firefox, Safari, and
  Linux/macOS browsers are expected to work but are **not verified**.
- No touch movement controls; touch-only phones/tablets are not supported.
- Viewports below 800×600 are not verified.

**Progression and saves**
- No timed autosave and no unload flush. A reload discards progress since the last save
  point; the start menu is always shown after a reload.
- Saves are origin- and browser-profile-scoped. “Clear site data”, a new profile, or a
  different browser starts a fresh game.
- Storage quota failures are logged to the console; there is no player-facing save-failure
  toast.
- No player-facing save export/import UI. The versioned transfer/backup API exists in the
  storage layer but is not wired to a menu.
- Long-session memory growth and thermal behavior are not soaked.

**PWA**
- Update activation is deliberate: a waiting build stays inactive until the player chooses
  “Save & Reload”.
- Updates are checked hourly while the app is open; a closed app does not update.
- Browsers may evict IndexedDB under storage pressure; the game does not request persistent
  storage.
- The local admin gate deters casual access only; it is not a security boundary.

**Content and localization**
- UI strings are centralized and text scaling is supported, but only English content ships.
- Educational questions are untranslated by design; question language is independent of UI
  language. No RTL layout support.

**Operations**
- Error logging is console-only; there is no remote telemetry, crash reporting, or PII
  collection. Field failures are invisible to developers.
- No online multiplayer, accounts, or cloud sync (Phase 30 is design-only).
- Deployment must be at the domain root over HTTPS (Section 5.1).

## 10. Save backup guidance

**Where saves live**

| Data | IndexedDB database | Notes |
| --- | --- | --- |
| Player save | `knowledge-realms-save` | Schema v6; includes profile, inventory, quests, settings |
| Question bank | `knowledge-realms-questions` | Admin-authored questions/overrides; bundled questions are always available |

Both are scoped to the deployment origin and the browser profile. The installed PWA shares
the same storage as the browser tab from the same origin.

**What deletes progress**

- Browser “Clear site data”, “Clear cookies and site data”, or private/incognito windows.
- Removing the browser profile or using a different browser/device.
- Storage eviction under disk pressure (the game does not request persistent storage).
- Uninstalling the PWA does not itself delete origin data, but some browsers offer to clear
  it during uninstall.

**Recommended operator guidance before upgrades, tests, or rollbacks**

1. Keep a browser-profile copy or a DevTools IndexedDB export of both databases.
2. Do not clear site data during a release; test migrations on a copy of a real profile.
3. After upgrading, confirm the save loads and the schema version is 6.
4. If a save is corrupted, the app attempts automatic repair and reports what was repaired;
   recovery cannot restore deleted data.

**Current product gap:** there is no one-click in-game backup/export button. The
`src/storage/SaveTransfer.ts` envelope and slot/backup storage methods are implemented and
tested, but they are not exposed in a menu. Until they are, backups are an operator task
(profile/DevTools), not a player feature.

## 11. Browser support statement

**Supported (verified):** desktop Chrome/Edge (Chromium) on Windows, keyboard required,
viewport ≥ 800×600, Canvas or WebGL, IndexedDB enabled. Verified in Chrome 156 headless
against the production build.

**Expected but not claimed:** desktop Firefox, desktop Safari 17+, Chromium on Linux/macOS,
with the same requirements. Not exercised in this project.

**Degrades gracefully:** IndexedDB blocked/absent → session-only play with an on-screen
notice; Web Audio unavailable → silent play; `crypto.randomUUID` unavailable → fallback ID
generator (IDs may be weaker but functional).

**Not supported:** touch-only phones and tablets (no on-screen movement controls); viewports
below 800×600; hosting under a sub-path; non-HTTPS production origins (service worker
requires a secure context).

**Not required:** network access after first load, cookies, cloud services, server-side
logic, or the History API (browser Back leaves the game).
