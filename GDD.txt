# PART I — FINAL GAME DESIGN DOCUMENT (GDD)

## 1. Game Concept

Knowledge Realms is a 2D fantasy action RPG inspired by classic games such as Zenonia.

Players explore a fantasy world, fight monsters, complete quests, collect equipment, develop professions, manage businesses, and improve their knowledge across different academic disciplines.

The game's distinguishing feature is its educational combat system: battles involve answering questions related to the subject of the monster's hunting zone.

Players have two distinct progression systems:

1. Character Level — developed primarily by defeating monsters and earning combat experience.
2. Knowledge Mastery — developed by answering educational questions and demonstrating subject knowledge.

These systems are connected but independent.

A player can have a high character level but relatively low mastery in Mathematics, for example. Likewise, a player can have strong Mathematics mastery without having an equally high character level.

## 2. Core Gameplay Loop

1. Select User mode.
2. Enter the world.
3. Explore towns, buildings, and hunting zones.
4. Find and initiate a monster battle.
5. Answer a randomized set of educational questions.
6. Receive damage or deal damage depending on the answer.
7. Defeat the monster and receive rewards.
8. Gain character EXP, Gold, items, and subject mastery EXP.
9. Improve equipment and abilities.
10. Enter more challenging zones and explore additional game systems.

## 3. Player Roles

The initial game has two entry options:

### User
- Play the game.
- Explore maps and buildings.
- Fight monsters.
- Answer questions.
- Gain experience and mastery.
- Manage inventory and equipment.
- Complete quests.
- Access available economy and business systems.

### Super Admin
- Add questions.
- View questions.
- Edit questions.
- Delete questions.
- Filter questions by educational tier, subject, topic, and question type.
- Import and export question data.

The first prototype will use a simple User / Super Admin role selector.

**Important:** This is not secure authentication. Anyone with access to the application can select Super Admin. Real authentication and authorization must be added before public deployment.

## 4. Character Progression

Character Level is primarily earned through combat EXP.

Possible EXP sources:
- Defeating monsters.
- Defeating bosses.
- Completing quests.
- Exploring designated areas.
- Completing selected achievements.

Monster grinding is the primary source of character EXP.

Character Level determines:
- General character progression.
- Access to recommended hunting areas.
- Monster difficulty comparisons.
- General RPG stat growth.
- Educational question difficulty adjustments during PvE.

Character statistics:
- HP
- MP
- Attack
- Defense
- Intelligence
- Critical Rate
- Movement Speed

The initial implementation should use configurable formulas rather than hardcoded progression values.

## 5. Knowledge Mastery

Each subject has its own independent mastery progression.

Initial disciplines:

1. Mathematics and Logic
2. General Knowledge
3. Science
4. Programming and Technology
5. Physics and Engineering
6. Business and Economics

Additional subjects can be added without changing the core progression system.

Example:

A player may have:
- Mathematics Mastery: Level 20
- Science Mastery: Level 8
- Programming Mastery: Level 15
- Business Mastery: Level 3

Mastery progression is performance-based.

### Mastery EXP rules

Correct answers can award mastery EXP.

The amount awarded depends on:
- Question difficulty.
- Educational tier.
- Answer correctness.
- Answering speed.
- Performance streak or combo, if enabled.

Recommended initial calculation:

Mastery EXP = Base Mastery EXP × Difficulty Multiplier × Speed Multiplier × Performance Multiplier

The exact multipliers must be configurable.

Initial rules:
- Correct answers award mastery EXP.
- Incorrect answers award zero mastery EXP.
- Faster correct answers may receive a speed bonus.
- More difficult questions award more mastery EXP.
- Repeatedly answering easy questions should not provide the same progression rate as answering challenging questions.
- Mastery EXP must be awarded only once per question attempt.

Mastery may eventually improve subject-related abilities, knowledge skills, and bonuses.

Character Level and Knowledge Mastery must not be merged into one EXP system.

## 9. PvE Question Difficulty System

This is a core mechanic of Knowledge Realms.

Question difficulty must consider BOTH:

1. Monster Level.
2. Difference between Player Level and Monster Level.

The system must not simply select questions using the player's level alone.

### 9.1 Base Educational Tier

The monster's level determines the baseline educational tier.

Example:

- Player Level 5 fighting Monster Level 5: Elementary baseline.
- Player Level 15 fighting Monster Level 15: Junior High baseline.
- Player Level 55 fighting Monster Level 55: Senior High baseline.

### 9.2 Level Difference

Calculate:

Level Difference = Monster Level − Player Level

Interpretation:
- Positive result: Monster is higher level than the player.
- Zero: Same level.
- Negative result: Monster is lower level than the player.

### 9.3 Higher-Level Monster Challenge Rule

When the player fights a monster significantly above their level, the question difficulty must increase sharply.

This is intentional. Higher-level monsters should challenge players with questions that may be far beyond their normal educational tier.

Recommended initial configurable difficulty-shift table:

| Monster Above Player | Additional Question Challenge |
|---|---|
| 1–2 levels | Slightly harder |
| 3–4 levels | Moderately harder |
| 5–9 levels | Major difficulty increase |
| 10–19 levels | May jump one or more educational tiers |
| 20+ levels | Very high challenge; may jump multiple tiers |

The difficulty shift must be configurable.

For example:

- Player Level 5 vs Monster Level 5: Elementary questions.
- Player Level 5 vs Monster Level 7: Harder Elementary questions.
- Player Level 5 vs Monster Level 10: Very challenging Elementary questions, potentially introductory questions from the next tier if the configured pool allows it.
- Player Level 5 vs Monster Level 15: Questions may jump to Junior High School.
- Player Level 5 vs Monster Level 30: Questions may be substantially above the player's normal tier.

The system must avoid selecting questions above the available content pool. If the required tier or difficulty has insufficient questions, use the nearest available valid question and record the fallback for debugging.

### 9.4 Lower-Level Monster Rule

When a high-level player fights a much lower-level monster:
- Questions should become easier relative to the monster's baseline tier.
- The system should avoid giving unnecessarily advanced questions.
- The monster should remain a low-level monster for reward and EXP calculations.
- Easy monsters must not become an unlimited high-efficiency mastery farming method.

### 9.5 Important Separation

The PvE system uses monster level and player-versus-monster level difference.

The PvP system uses the separate reverse-difficulty rule described later.

Do not reuse the PvP reverse-difficulty formula for PvE.

## 10. Battle System

Combat uses a hybrid system.

Players can explore and perform basic actions without answering questions. Educational questions are integrated into monster battles.

### 10.1 Battle Sequence

1. Player initiates a fight.
2. Game identifies the monster and its configuration.
3. Game calculates the educational tier and difficulty.
4. Game randomly determines the number of questions for that battle.
5. A question appears with a countdown timer.
6. Player submits an answer.
7. Game evaluates the answer.
8. If correct, the player attacks the monster.
9. If incorrect or the timer expires, the player takes damage.
10. The battle continues until the monster or player is defeated.

### 10.2 Random Question Count

The number of questions per monster battle is randomized.

The random range depends on monster characteristics, especially HP and battle difficulty.

Recommended initial example:

| Monster Type | Suggested Question Count |
|---|---|
| Weak monster | 2–3 |
| Normal monster | 3–5 |
| Strong monster | 4–7 |
| Elite monster | 5–8 |
| Boss | 6–10 |

These values are starting configuration values, not fixed balance rules.

The number of questions must be determined when the battle begins and remain fixed for that battle.

The system must not reroll the total question count after every answer.

### 10.3 Correct Answer

A correct answer allows the player to attack.

Damage can depend on:
- Player Attack.
- Monster Defense.
- Character Level.
- Subject Mastery.
- Equipment.
- Critical chance.
- Question difficulty.
- Performance bonuses.

### 10.4 Incorrect Answer

The selected rule is DAMAGE-PLAYER.

When the player answers incorrectly:
- The player receives damage from the monster.
- The question attempt is consumed.
- The monster remains alive unless a separate battle rule causes otherwise.
- The next battle question proceeds if the player survives and questions remain.

Timeouts should initially use the same penalty as an incorrect answer.

### 10.5 Victory and Defeat

Victory:
- Award monster EXP.
- Award Gold.
- Roll item drops.
- Award eligible subject mastery EXP from correct answers.
- Update quest progress.

Defeat:
- End the battle.
- Apply the configured defeat penalty.
- Do not award monster victory rewards.

All rewards must be handled by the game rules system, not by the visual interface.

## 11. Question Types

The question system supports:

1. Multiple Choice
2. Identification
3. Essay

### Multiple Choice
- One correct answer initially.
- Multiple answer options.
- Correct answer identified by a stable choice ID.
- Option order may be randomized.

### Identification
- Player enters a text answer.
- Comparison should ignore case and unnecessary leading/trailing spaces.
- Multiple accepted answer aliases may be supported.

### Essay
- Player enters a longer response.
- Store the expected answer, explanation, and grading reference.
- Initial version should not depend on AI grading.
- Essay questions are best suited for quests, research, training, and special learning activities.

For the initial fast-paced monster combat system, use Multiple Choice and Identification by default. Essay questions should be excluded from ordinary random combat selection unless explicitly configured for a special encounter.

## 13. Super Admin Question Management

Super Admin should have a simple dashboard.

Initial required functions:
- Add question.
- View/list questions.
- Delete question.

Recommended additional functions:
- Edit question.
- Search and filter.
- Import JSON.
- Export JSON.

Filters:
- Educational tier.
- Subject.
- Topic.
- Difficulty.
- Question type.
- Publication status.

The question management system must be separate from the battle question retrieval system.

### Storage Rules

Bundled JSON files provide initial question content.

IndexedDB stores local changes, additions, and overrides.

The application must preserve admin changes after refresh or restart.

Deleting a bundled question must not cause it to reappear after reloading the application. Use a deletion record or tombstone mechanism.

Importing questions must validate the file before saving.

Exporting questions must produce a usable JSON backup.

## 14. Zone Access

The selected rule is RISK ACCESS.

Players may enter higher-level zones even when below the recommended level.

However:
- The zone must clearly display its recommended level.
- The player must receive a warning before entering a dangerous zone.
- Monsters can be much stronger than the player.
- Question difficulty can jump substantially under the higher-level monster rule.
- The player can be defeated quickly.
- Rewards should remain consistent with the monster's actual level and challenge.

Do not automatically prevent entry merely because the player's level is too low.

## 15. PvP System

PvP is a future feature, not required for the first playable version.

The selected PvP difficulty rule is REVERSE DIFFICULTY.

The lower-level player receives harder questions.

The higher-level player receives easier questions.

This is an intentional design decision and must not be silently replaced with equalized or standard difficulty.

PvP will eventually support:
- Casual matches.
- Ranked matches.
- Knowledge duels.
- Survival challenges.
- Tournaments.
- Championships.

The exact PvP scoring, damage, and balancing formula remains configurable and must be designed separately from PvE.

The first version should not implement online PvP.

## 20. Technical Architecture

Recommended stack:

- Phaser 3: 2D game rendering and game scenes.
- TypeScript: game logic and data structures.
- Vite: development server and build system.
- HTML/CSS: menus and administrative interface.
- JSON: bundled static content.
- IndexedDB: local persistent data.
- Git: version control.

The project should be modular.

Game rules must be separated from visual rendering.

Recommended modules:

- core
- player
- world
- maps
- monsters
- combat
- questions
- mastery
- admin
- inventory
- equipment
- quests
- economy
- storage
- UI

Each module must have a clearly defined responsibility and public interface.

The question system must not depend on Phaser scenes.

The combat rules must not directly manipulate HTML elements.

The admin interface must not directly modify the battle engine.

## 21. Development Principles

1. Build one small feature at a time.
2. Do not implement several unrelated systems in one task.
3. Inspect the existing project before changing files.
4. Keep modules independent.
5. Use TypeScript types and validation.
6. Avoid unnecessary dependencies.
7. Do not rewrite working code without a clear reason.
8. Run relevant tests after each task.
9. Run type checking and build checks at appropriate milestones.
10. Update documentation when interfaces or rules change.
11. Keep configuration values separate from business logic.
12. Never silently change an approved game mechanic.
13. Do not implement future features prematurely.
14. Ask before making major architectural changes.

# PART V — FINAL APPROVED MECHANICS SUMMARY

| Mechanic | Final Decision |
|---|---|
| Starting map | Beginners Village |
| Starting level range | 1–10 |
| Character EXP | Primarily monster grinding |
| Knowledge mastery | Separate per subject |
| Mastery EXP | Performance-based |
| PvE educational tier | Based on monster level |
| Higher-level monster | Can cause major difficulty jumps |
| Lower-level monster | Questions adjust easier |
| Battle question count | Random, based on monster HP/category |
| Correct answer | Player attacks |
| Incorrect answer | Player receives damage |
| Timeout | Same initial penalty as incorrect answer |
| Zone access | Higher-level zones allowed with danger warning |
| Combat question types | Multiple Choice and Identification by default |
| Essay questions | Quests, research, and special activities by default |
| Admin access | User / Super Admin role selector |
| Question storage | JSON + IndexedDB |
| Initial game mode | Offline-first single-player |
| PvP | Future feature |
| PvP difficulty | Reverse difficulty |
| Initial game engine | Phaser 3 |
| Language | TypeScript |
| Build tool | Vite |

## Final Design Principle

Knowledge Realms must remain modular and expandable.

The core experience should be completed before advanced systems are introduced.

Every new feature should integrate with existing modules through clearly defined interfaces.

The educational question system, character progression, knowledge mastery, battle system, and administrative tools must remain independently testable.

The goal of the first release is not to build the entire fantasy world immediately. It is to create one polished, working gameplay loop that can serve as the foundation for the rest of Knowledge Realms.
